¿Qué es serverless?

Serverless no significa "sin servidores": significa que tú no los administras. Escribes funciones pequeñas, la nube las ejecuta cuando ocurre un evento, escala sola y cobra por uso.

⚡ FaaS y triggers

Function as a Service: unidades de código que se ejecutan ante un trigger (HTTP, cola, temporizador, cambio en una base de datos).

En este lab: api/src/functions/*.js, todas con trigger HTTP.

🧊 Cold start

Si no hay una instancia lista, la plataforma crea una: carga runtime y código. Esa primera llamada es más lenta.

Obsérvalo: pestaña 2, campo coldStart.

🫙 Stateless

La memoria de una instancia es temporal y no se comparte. El estado duradero va en un servicio externo (Firestore, Cloud Storage…).

Obsérvalo: el contador invocationsOnThisInstance se reinicia.

📈 Escalado automático

Ante más tráfico, la plataforma agrega instancias (scale-out) y luego las retira (incluso hasta cero).

Obsérvalo: botón "Ráfaga" y los distintos instanceId.

💸 Pago por uso

Pagas ejecuciones y tiempo de cómputo, no máquinas encendidas. Sin tráfico, costo de cómputo ≈ 0.

En este lab: capa gratuita de Cloud Run (2 M de peticiones/mes).

🌐 Firebase Hosting

CDN global para HTML/CSS/JS que, con rewrites, enruta /api/* a las funciones en el mismo dominio (sin CORS).

En este lab: src/ (sitio), api/ (funciones) y firebase.json (rutas).

Experimentos guiados
  1. Cold start: espera ~20 min sin usar el sitio e invoca una vez. ¿coldStart es true? ¿La latencia es mayor que en la segunda llamada?
  2. Stateless: anota el valor de invocationsOnThisInstance. Haz un nuevo despliegue (un commit) y vuelve a invocar. ¿Qué pasó con el contador?
  3. Escalado: lanza varias ráfagas. ¿Cuántos instanceId distintos aparecen? (Compáralo con labels.instanceId en Cloud Logging.)

Preguntas

Las preguntas llegan desde GET /api/questions sin la respuesta. Al enviar cada formulario, POST /api/answer califica en el servidor y devuelve la explicación.

CI/CD sin llaves de acceso

El pipeline no guarda claves JSON de cuentas de servicio. Usa Workload Identity Federation: GitHub firma un token OIDC de corta duración y Google lo cambia por un token temporal de una cuenta de servicio que solo confía en este repositorio.

  1. 1
    git push / Pull Request
    Cambias código en src/ o api/.
  2. 2
    GitHub Actions — job test
    npm test valida la lógica de las funciones. Si falla, no se despliega.
  3. 3
    Job deploy
    google-github-actions/auth obtiene un token temporal (WIF); gcloud functions deploy publica las 4 funciones y firebase deploy publica src/.
  4. 4
    Producción o preview
    Push a main → producción. Pull Request → funciones *-pr-N y canal de preview con URL propia.
  5. 5
    Job close_preview
    Al cerrar el PR, se borran las funciones y el canal de preview.
